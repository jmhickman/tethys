# Gatekeeper — codebase context

## Purpose
`gatekeeper` is a root-run egress-control daemon for an AI-agent sandbox. It owns an nftables
table that blocks outbound traffic for one policed `agent_user` uid, keeps a SQLite grant ledger,
and lets an unprivileged agent request time-boxed network grants through an MCP server (`gk-mcp`)
which forwards requests to the daemon over a Unix socket (`mcp.sock`). A human approves on
`admin.sock` (0600, root-only) via `gk-tui`.

## Scope
Finding scope: `crates/` (workspace members `core`, `gatekeeper`, `gk-mcp`, `gk-tui`; ~6.4 KLoC,
17 `.rs` files). `target/` build artifacts are out of scope. Repo root (`.`) is read-only context:
`Cargo.toml`, `config.example.toml`, `deploy/`, shell e2e scripts. Findings outside `crates/` are
out of scope.

## Entry points
- **`mcp.sock` (Unix socket)** — JSON protocol from `gk-mcp` (runs as the *unprivileged harness /
  agent user*, same uid as the agent). Peer identity checked via `SO_PEERCRED` against `mcp_user`.
  Fully attacker-controlled input: `crates/gatekeeper/src/server.rs`, wire framing in
  `crates/core/src/wire.rs`, message types in `crates/core/src/protocol.rs` (serde deserialization).
- **`admin.sock`** — trusted approver channel (0600, root only): `crates/gatekeeper/src/admin.rs`.
- **Config file** `/etc/gatekeeper/config.toml` (root-owned; parse in `crates/gatekeeper/src/config.rs`).
- **CLI args** on all four binaries (clap); `gk-mcp` also speaks MCP stdio with the agent harness
  (`crates/gk-mcp/src/main.rs`, rmcp).
- **Filesystem**: DB path, socket paths, nft rule files (`install.rs`, `ledger.rs` rusqlite,
  `reconcile.rs`, `core/src/nft.rs` shells out to `nft`/`ip` and parses their output).

## Trust boundaries
Attacker = unprivileged local user (the agent uid) who can: connect to `mcp.sock` with arbitrary
framed JSON, spawn/talk to `gk-mcp` over stdio, influence anything the agent side controls.
NOT a boundary: `mcp_user` vs agent uid (same user in standard topology). The privilege boundary
is the root daemon and its 0600 `admin.sock`; crossing it (forged approval, grant TTL bypass,
uid-scope escape in nft rules, ledger corruption causing fail-open) is the interesting attack.
Root-side files (`/etc/gatekeeper/*`, `/run/gatekeeper`) are not attacker-writable.

## Existing hardening
- Fail-safe posture documented: unresolvable `agent_user` ⇒ host-wide enforcement; missing
  `mcp_user` stops startup.
- `SO_PEERCRED` uid gating on `mcp.sock`; socket mode 0600 on `admin.sock`.
- TTL ceiling (`max_ttl`), approver timeout auto-deny.
- e2e scripts (`e2e_test.py`, `mcp_e2e.sh`, `pin_e2e.sh`) — manual integration tests.
- No fuzzing harness, no MIRI runs, no `cargo-audit`/`cargo-deny` config found; no
  `#![forbid(unsafe_code)]` observed in scope. Pure safe Rust (no `unsafe`, no FFI in `crates/`).
